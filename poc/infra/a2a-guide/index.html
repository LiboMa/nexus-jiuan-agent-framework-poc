AAA2A 协议

Agent2Agent 协议开发者指南

一个开放协议，让不同框架、不同厂商的智能体互相发现、委派任务、交付结果，而不必暴露各自的内部实现。

规范 v1.0.0由 Google 发起，现由 Linux 基金会托管JSON-RPC、gRPC、HTTP+JSON 三种绑定


    

  

  
上图是一次完整的 A2A 流式调用：先读取对方的名片，再发消息，最后通过 SSE 一边接收进度一边接收产出。右侧是每一步真实的线上报文。







  
为什么需要 A2A

  

    
企业里的智能体越来越多：有的用 Strands 写，有的用 LangGraph、ADK、CrewAI，有的是供应商提供的 SaaS。每对智能体之间都写一套私有对接，N 个智能体就要维护 N² 条集成。A2A 把这件事标准化：任何智能体只要暴露一张 Agent Card，再实现一组固定的方法，就能被其他智能体发现和调用。

    
A2A 的关键设计是不透明执行：调用方只看到对方声明的技能、任务状态和产出，看不到对方的提示词、工具、记忆和推理过程。这让跨团队、跨公司的协作成为可能。

  


  

    
    

      
MCP 与 A2A 不是二选一。MCP（Model Context Protocol）解决“智能体如何使用工具和数据”，A2A 解决“智能体如何与另一个有自主性的智能体协作”。一个典型系统里，智能体对下用 MCP 接工具，对外用 A2A 接其他智能体。

      

        
MCPA2A

        
          
对端是什么工具、资源、提示词另一个智能体

          
交互粒度一次函数调用一个可能持续数天的任务

          
状态基本无状态Task 有完整生命周期

          
对端可见性输入输出 schema 完全公开只公开技能描述，内部不透明

        
      

    

  







  
核心对象

  
A2A 的数据模型只有六个概念。理解它们之间的包含关系，就理解了整个协议。

  

    

      
Context 上下文 contextId

      
一段会话。同一 contextId 下的多个任务共享背景，由服务端生成。

      

        
Task 任务 id · status · history · artifacts

        

          

            
TaskStatus

            
state、timestamp，可附带一条 Message（例如追问用户）

          

          

            
Message 消息

            
role：ROLE_USER 或 ROLE_AGENT，一轮沟通

            
PartPart

          

          

            
Artifact 产出物

            
任务的交付结果，可分块流式生成

            
PartPart

          

        

      

    

    

      

        
Part 内容片段

        
每个 Part 恰好包含以下之一，另可带 mediaType、filename、metadata：

        
textraw（base64 字节）url（文件链接）data（任意 JSON）

      

      

        
Agent Card
智能体的公开名片，描述身份、技能、接口地址与认证方式。

        
Task
工作单元，有唯一 id 和状态机。客户端发消息，服务端决定是否创建任务。

        
Message
用于沟通：提问、补充说明、进度说明。不是交付物。

        
Artifact
用于交付：报告、文件、结构化数据。

      

    

  

  
Message 和 Artifact 的区分很重要：沟通走 Message，结果走 Artifact。客户端据此可以把“智能体在说什么”和“智能体做出了什么”分开渲染、分开存储。







  
发现：Agent Card

  

    
每个 A2A 服务端在固定路径公开一份 JSON 名片：

  

  
GET https://{域名}/.well-known/agent-card.json

  
客户端读取名片后就知道：这个智能体能做什么（skills）、去哪里调用（supportedInterfaces）、用什么协议绑定、要什么凭证（securitySchemes）、支不支持流式和推送（capabilities）。除了 well-known 路径，也可以通过注册中心或直接配置获取名片。

  
{
  "name": "差旅规划智能体",
  "description": "根据日程与预算规划行程并给出报价",
  "version": "2.1.0",
  "provider": { "organization": "Example Travel", "url": "https://example.com" },
  "supportedInterfaces": [
    { "url": "https://travel.example.com/a2a/v1", "protocolBinding": "JSONRPC",   "protocolVersion": "1.0" },
    { "url": "https://travel.example.com/rest",   "protocolBinding": "HTTP+JSON", "protocolVersion": "1.0" },
    { "url": "travel.example.com:443",            "protocolBinding": "GRPC",      "protocolVersion": "1.0" }
  ],
  "capabilities": { "streaming": true, "pushNotifications": true, "extendedAgentCard": true },
  "securitySchemes": {
    "corp-oidc": { "openIdConnectSecurityScheme": {
      "openIdConnectUrl": "https://login.example.com/.well-known/openid-configuration" } }
  },
  "securityRequirements": [ { "schemes": { "corp-oidc": { "list": ["openid", "profile"] } } } ],
  "defaultInputModes":  ["text/plain"],
  "defaultOutputModes": ["text/plain", "application/json"],
  "skills": [{
    "id": "plan-trip",
    "name": "行程规划",
    "description": "输入出发地、目的地、日期与预算，返回交通和酒店方案",
    "tags": ["travel", "booking"],
    "examples": ["下周二去上海出差两天，预算 3000 元"],
    "outputModes": ["application/json"]
  }]
}

  

    
字段必填作用

    
      
name description version是身份信息。description 会被调用方的 LLM 用来判断“该不该把任务交给它”，要写清楚。

      
supportedInterfaces是有序列表，排在前面的是首选。每项含 url、protocolBinding（JSONRPC／GRPC／HTTP+JSON）、protocolVersion，可选 tenant。

      
capabilities是streaming、pushNotifications、extendedAgentCard、extensions。客户端调用前应先检查。

      
defaultInputModes defaultOutputModes是接受与产出的媒体类型（MIME）。技能可以单独覆盖。

      
skills是技能清单：id、name、description、tags 必填，examples 强烈建议填写。

      
securitySchemes securityRequirements否认证方式声明，结构沿用 OpenAPI 的安全方案。

      
signatures否对名片的 JWS 签名，用于防篡改和验证发布者身份。

    
  







  
接口规范

  

    
v1.0 先用协议无关的方式定义了 11 个操作，再规定它们在三种绑定上的写法。服务端可以只实现一种绑定，也可以同时实现多种，在 Agent Card 的 supportedInterfaces 中声明。三种绑定在功能上必须等价。

  

  

    
操作（JSON-RPC method ＝ gRPC rpc）HTTP+JSON用途

    
      
SendMessagePOST /message:send发送消息，开始或继续一个任务。返回 Task 或 Message。

      
SendStreamingMessagePOST /message:stream同上，但用 SSE（gRPC 为 server stream）持续推送事件。需 capabilities.streaming。

      
GetTaskGET /tasks/{id}查询任务状态与产出，可用 historyLength 控制返回的历史条数。

      
ListTasksGET /tasks按 contextId、状态等条件分页列出任务。

      
CancelTaskPOST /tasks/{id}:cancel请求取消。已结束的任务返回 TaskNotCancelableError。

      
SubscribeToTaskPOST /tasks/{id}:subscribe¹重新订阅进行中任务的事件流，用于断线重连。

      
CreateTaskPushNotificationConfigPOST /tasks/{id}/pushNotificationConfigs为任务注册 webhook。需 capabilities.pushNotifications。

      
GetTaskPushNotificationConfigGET /tasks/{id}/pushNotificationConfigs/{configId}查询某个 webhook 配置。

      
ListTaskPushNotificationConfigsGET /tasks/{id}/pushNotificationConfigs列出任务的全部 webhook 配置。

      
DeleteTaskPushNotificationConfigDELETE /tasks/{id}/pushNotificationConfigs/{configId}删除 webhook 配置。

      
GetExtendedAgentCardGET /extendedAgentCard认证后获取更完整的名片（例如只对内部用户开放的技能）。

    
  

  
¹ 规范正文表格写作 POST，a2a.proto 的 HTTP 注解写作 GET，实现时以所用 SDK 为准。所有 HTTP 路径都可以加 /{tenant} 前缀，用于多租户路由。


  
同一次调用，三种写法

  
下面是同一个 SendMessage 请求在三种绑定上的样子。注意 JSON 字段统一用 camelCase，枚举值统一用 TASK_STATE_*、ROLE_* 这样的大写形式。

  

    
    
    
  

  


POST /a2a/v1 HTTP/1.1
Host: travel.example.com
Content-Type: application/json
A2A-Version: 1.0
Authorization: Bearer eyJhbGciOi...

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "SendMessage",
  "params": {
    "message": {
      "messageId": "9b1f6c1e-0d4e-4f35-9c0a-1f0e2a7b3c55",
      "role": "ROLE_USER",
      "parts": [{ "text": "下周二去上海出差两天，预算 3000 元" }]
    },
    "configuration": { "acceptedOutputModes": ["application/json", "text/plain"] }
  }
}

// 响应：result 中恰好包含 task 或 message 之一
{ "jsonrpc": "2.0", "id": 1,
  "result": { "task": { "id": "t-9f2", "contextId": "c-41a",
              "status": { "state": "TASK_STATE_COMPLETED" }, "artifacts": [ ... ] } } }

    
所有方法都发到 Agent Card 中声明的同一个 URL，用 method 区分。错误放在标准的 JSON-RPC error 对象里。

  

  


POST /rest/message:send HTTP/1.1
Host: travel.example.com
Content-Type: application/a2a+json
A2A-Version: 1.0
Authorization: Bearer eyJhbGciOi...

{
  "message": {
    "messageId": "9b1f6c1e-0d4e-4f35-9c0a-1f0e2a7b3c55",
    "role": "ROLE_USER",
    "parts": [{ "text": "下周二去上海出差两天，预算 3000 元" }]
  },
  "configuration": { "acceptedOutputModes": ["application/json", "text/plain"] }
}

// 响应 200 OK，Content-Type: application/a2a+json
{ "task": { "id": "t-9f2", "contextId": "c-41a",
            "status": { "state": "TASK_STATE_COMPLETED" }, "artifacts": [ ... ] } }

    
资源化路径加 Google AIP 风格的自定义动词（:send、:cancel）。错误用 HTTP 状态码表达，例如任务不存在返回 404。

  

  


// 服务定义：package lf.a2a.v1
service A2AService {
  rpc SendMessage(SendMessageRequest) returns (SendMessageResponse);
  rpc SendStreamingMessage(SendMessageRequest) returns (stream StreamResponse);
  rpc GetTask(GetTaskRequest) returns (Task);
  // ... 其余 8 个 rpc
}

# 用 grpcurl 调用，版本号放在 metadata 里
grpcurl -H 'a2a-version: 1.0' -H 'authorization: Bearer eyJhbGciOi...' \
  -d '{"message":{"messageId":"9b1f...","role":"ROLE_USER",
       "parts":[{"text":"下周二去上海出差两天，预算 3000 元"}]}}' \
  travel.example.com:443 lf.a2a.v1.A2AService/SendMessage

    
适合内部高吞吐场景。a2a.proto 是 v1.0 的权威数据定义，JSON 结构就是它按 proto3 JSON 规则映射出来的。错误映射到 gRPC 状态码并附带 google.rpc.ErrorInfo。

  


  
每次请求都要带的头

  

    
A2A-Version
客户端必须发送，值为 主版本.次版本，例如 1.0。服务端按该版本的语义处理，不支持则返回 VersionNotSupportedError。头为空时按 0.3 处理，以兼容旧客户端。也可以作为查询参数传递。

    
A2A-Extensions
可选，逗号分隔的扩展 URI 列表，表示客户端希望启用的扩展。

    
Authorization
按 Agent Card 中声明的安全方案携带凭证。身份信息走 HTTP 层，不放进 A2A 消息体。

  







  
任务生命周期

  
每个 Task 都有一个状态。点击右侧场景，看任务如何在状态之间流转；点击任一状态查看含义。

  

    
    

      
选一个场景

      

      
任务有三类状态：进行中（SUBMITTED、WORKING）、中断等待（INPUT_REQUIRED、AUTH_REQUIRED）、终态（COMPLETED、FAILED、CANCELED、REJECTED）。进入终态后任务不可再变化，后续沟通要创建新任务。

    

  

  
进行中中断：等待客户端终态：不可再变化

  
SendMessage 默认会一直等到任务进入终态或中断状态才返回。把 configuration.returnImmediately 设为 true，则创建任务后立即返回，之后用轮询、订阅或推送拿结果。







  
交互方式

  
同一套对象，四种拿结果的方式。按任务时长和客户端的网络条件选择。

  

    
方式用到的操作适合

    
      
同步等待SendMessage（必要时轮询 GetTask）秒级完成的任务；客户端在防火墙后、无法接 webhook

      
流式 SSESendStreamingMessage、SubscribeToTask需要实时展示进度和逐字产出的交互式场景

      
异步推送returnImmediately ＋ webhook、GetTask分钟到天级的长任务；移动端、Serverless 客户端

      
多轮对话带 taskId／contextId 再次 SendMessage智能体缺信息、需要人确认或需要额外授权

    
  

  

    
    
    
    
  

  

  

  

  







  
安全、扩展与版本

  

    
A2A 把智能体当成普通的企业 Web 服务对待，安全全部复用现有标准，不发明新机制。生产环境必须使用 HTTPS／TLS，推荐 TLS 1.3。

  

  
认证方式

  

    
securitySchemes 中的类型说明

    
      
apiKeySecuritySchemeAPI Key，放在 header、query 或 cookie 中

      
httpAuthSecuritySchemeHTTP 认证，如 Bearer（JWT）、Basic

      
oauth2SecuritySchemeOAuth 2.0：授权码、客户端凭证、设备码等流程

      
openIdConnectSecuritySchemeOIDC，提供 discovery 地址

      
mtlsSecurityScheme双向 TLS，适合服务间调用

    
  

  

    
凭证获取
客户端在协议之外拿到凭证（OAuth 流程、密钥管理系统等），再放进 HTTP 头。任务执行中如需额外授权，任务进入 TASK_STATE_AUTH_REQUIRED。

    
扩展名片
公开名片只放可公开的信息；设置 capabilities.extendedAgentCard: true 后，已认证的客户端可通过 GetExtendedAgentCard 拿到完整技能列表。

    
名片签名
signatures 字段携带 JWS 签名，客户端验证后可确认名片未被篡改、确由声明的发布者签发。

    
推送安全
webhook 请求按 TaskPushNotificationConfig.authentication 携带凭证；客户端须校验 taskId 和 token，且要按幂等方式处理，因为可能重复投递。服务端应防范 SSRF，校验 webhook 地址。

    
扩展机制
名片在 capabilities.extensions 中用 URI 声明扩展（可标记 required），客户端通过 A2A-Extensions 头启用。必需扩展未启用时返回 ExtensionSupportRequiredError。

    
版本协商
服务端可以为同一绑定暴露多个版本的接口，在 supportedInterfaces 中分别声明 protocolVersion。补丁版本号不参与协商。

  







  
错误码

  
除 JSON-RPC 标准错误（-32700 解析错误、-32600 无效请求、-32601 方法不存在、-32602 参数无效、-32603 内部错误）外，A2A 定义了以下业务错误，在三种绑定上有固定映射：

  

    
错误JSON-RPCgRPCHTTP何时出现

    
      
TaskNotFoundError-32001NOT_FOUND404任务 id 不存在或已过期

      
TaskNotCancelableError-32002FAILED_PRECONDITION400任务已处于终态

      
PushNotificationNotSupportedError-32003FAILED_PRECONDITION400服务端未开启推送

      
UnsupportedOperationError-32004FAILED_PRECONDITION400调用了未实现的操作，如未开启流式却调用流式接口

      
ContentTypeNotSupportedError-32005INVALID_ARGUMENT400Part 的媒体类型不被接受

      
InvalidAgentResponseError-32006INTERNAL500智能体产生了不符合规范的响应

      
ExtendedAgentCardNotConfiguredError-32007FAILED_PRECONDITION400请求扩展名片但服务端未配置

      
ExtensionSupportRequiredError-32008FAILED_PRECONDITION400客户端未启用必需的扩展

      
VersionNotSupportedError-32009FAILED_PRECONDITION400A2A-Version 指定的版本不受支持

    
  







  
动手实现

  

    
官方 SDK 覆盖 Python（a2a-sdk）、JavaScript／TypeScript、Java、Go、.NET。如果你已经在用 Strands Agents，它内置了 A2A 服务端和客户端，几行代码就能接入。以下示例基于 strands-agents 1.54。

  

  
把 Strands 智能体发布为 A2A 服务


# pip install 'strands-agents[a2a]'
from strands import Agent
from strands.multiagent.a2a import A2AServer

travel = Agent(
    name="差旅规划智能体",
    description="根据日程与预算规划行程并给出报价",  # 会写进 Agent Card
    tools=[search_trains, search_hotels],
)

server = A2AServer(
    agent=travel,
    host="0.0.0.0",
    port=9000,                                   # 默认 9000
    http_url="https://travel.example.com/",       # 对外地址，经负载均衡时填写
    version="2.1.0",
)
server.serve()   # 或 server.to_fastapi_app() 挂到已有应用中

  
需要按会话隔离状态时，传 agent_factory=lambda context_id: Agent(...) 代替 agent，每个 contextId 会获得独立的智能体实例。


  
调用远程 A2A 智能体


from strands import Agent
from strands.agent import A2AAgent

travel = A2AAgent(endpoint="https://travel.example.com/")   # 自动读取 Agent Card
result = travel("下周二去上海出差两天，预算 3000 元")

# 也可以作为编排者的工具，由 LLM 决定何时委派
assistant = Agent(tools=[travel])


  
不用 SDK，直接用 curl 验证


# 1. 读取名片
curl -s https://travel.example.com/.well-known/agent-card.json | jq .

# 2. 流式发送消息（JSON-RPC 绑定）
curl -N https://travel.example.com/a2a/v1 \
  -H 'Content-Type: application/json' -H 'A2A-Version: 1.0' \
  -d '{"jsonrpc":"2.0","id":1,"method":"SendStreamingMessage",
       "params":{"message":{"messageId":"m-1","role":"ROLE_USER",
       "parts":[{"text":"下周二去上海出差两天"}]}}}'


  
服务端实现清单

  
    
    
  • 名片里的 description 和 skills[].examples 决定了调用方 LLM 能否正确路由，像写 API 文档一样认真写。
    • 
    
  • 每条消息都有 messageId，服务端应据此去重，客户端重试才安全。
    • 
    
  • 长任务务必支持 returnImmediately 或推送，否则调用方的 HTTP 连接会超时。
    • 
    
  • Task 存储要持久化（SDK 默认的内存存储重启即丢），否则 GetTask 和断线重连都会失效。
    • 
    
  • 记录 A2A-Version，并在名片中如实声明 protocolVersion。部分 SDK 的线上格式仍是 0.3，混用时要确认版本协商结果。
    • 
    
  • 部署到 Amazon Bedrock AgentCore Runtime 时可选择 A2A 协议，平台负责托管、伸缩和认证。
    • 
  







  
从 0.3 迁移到 1.0

  
网上很多教程和早期 SDK 用的是 0.2／0.3 的写法。对照下表识别：

  

    
项目0.3 及更早1.0

    
      
JSON-RPC 方法名message/send、message/stream、tasks/get、tasks/resubscribeSendMessage、SendStreamingMessage、GetTask、SubscribeToTask

      
枚举值"completed"、"input-required"、"user"TASK_STATE_COMPLETED、TASK_STATE_INPUT_REQUIRED、ROLE_USER

      
Part 结构用 "kind": "text" | "file" | "data" 区分不再有 kind，text／raw／url／data 四选一

      
接口声明url ＋ preferredTransport ＋ additionalInterfaces统一为有序的 supportedInterfaces

      
同步与异步configuration.blockingconfiguration.returnImmediately（语义相反，默认等待）

      
新增能力ListTasks、多租户 tenant、A2A-Version 版本协商、统一错误映射

现在的「自动展示」，靠的是 REST 列表加本机配置的调用密钥。A2A 只在已经知道发布编号以后才派得上用场：读名片和调用。按你定的方式改：每个用户用自己的 API 密钥连接 Nexus，看到自己的发布，自己挑 Agent、填调用密钥来启用。启用时当场验证，启用后立即可用；在 Nexus 上新发布或改了 Agent，刷新就能看到。不改文件，不部署，也不重启。

1现在怎么自动展示

PoC 服务端在两个时机取数：启动时，以及有人点「刷新」时。浏览器打开「Nexus Agent」页时，读的只是服务端的快照。

2卡在哪

A2A 本身没有目录

名片要先知道地址才能读，A2A 协议里没有「列出我的 Agent」的标准接口。Nexus 的 MCP 也一样，每个发布一个地址，地址下只有一个 ask。所以「有哪些 Agent」只能问 REST。

程序拿不到调用密钥

签发调用密钥只认网页登录的本人，Operator 用的 API 密钥会被拒（access_credential_service.py:283-286）。所以每个新 Agent 都要人工签发、交接、写文件、部署。

身份对不上

列表是按 EC2 那把 API 密钥的主人（admin）读的。九安的所有用户看到同一份列表，和他们自己是谁无关。

3三条身份线

应用用户和 Nexus 用户的对应关系，就是「这把 API 密钥的主人」。读列表和调用用的是两把不同的密钥，互相独立。

九安登录（PoC 是口令；生产是钉钉）
应用
应用用户
自己的 API 密钥 nxc_：读出我的发布，加上分享给我的发布
Nexus
应用
每个启用的发布一把 A2A 调用密钥 nxa_，由用户填写，加密保存
发布
  • 浏览器只在填写时经手密钥一次；服务端不回显密钥，页面上只显示指纹。
  • 每个用户有独立的 CLI 凭证目录和启用清单，看不到、也用不了别人的。
  • 断开 Nexus 连接，已经启用的 Agent 照样能用；停用某个 Agent，也不影响列表。
  • Nexus 只认发布者，费用也记在发布者名下；「谁调用的」由应用记在运行记录里。

4配置文件、注册，还是用户自己启用

方案怎么做谁看得到哪些 Agent闭环密钥在哪要改 Nexus
A 配置文件自动同步继续改 secrets.env，同步到实例后重新读取所有人看同一份不完整：改文件、同步都靠手工本机、构件桶、实例不用
B1 管理员统一注册（v1 草案）EC2 用一把管理员 API 密钥列出 Agent，由管理员逐个注册所有人看同一份完整实例（加密）不用
B2 用户自己连接并启用（你定的）用户填自己的 API 密钥，看到自己的发布；挑 Agent、填调用密钥来启用按自己的 Nexus 身份完整：只差在网页上签发调用密钥实例，按用户分开加密保存不用
C Nexus 原生Skills 或程序签发调用密钥，或者换取短期令牌按身份完整，全自动不保存长期密钥要

启动必需的东西放在配置文件里：账号口令，以及新增的调用密钥加密密钥 REGISTRY_KEY。Agent 的接入，由用户自己在页面上连接、启用。

5启用怎么闭环

连接只做一次：填自己的 API 密钥，应用用 CLI 登录，执行 whoami，再读出发布列表。之后每启用一个 Agent，过程如下：

#用户（Agent 开发者）应用服务端Nexus
1在「我的已发布 Agent」里点「启用」，填入调用密钥
2确认这个发布在我的列表里，A2A 地址和 Nexus 同源
3读 A2A 名片发布可调用、A2A 打开、所有者和 Agent 都可用时，才返回名片
4用这把密钥发 tasks/get，任务编号随机生成先认证、再分发（a2a_endpoint.py:528）：返回「任务不存在」说明密钥有效，返回 401 说明无效
5AES-256-GCM 加密，存进这个用户的启用清单，写留痕
6读能力清单（默认勾选）运行一轮 describe，约 0.03 美元
7卡片变成「已启用」，调用测试里立即出现刷新这个用户的视图
  • 迭代：在 Nexus 上新发布的 Agent，刷新后出现在列表里。改了的 Agent，发布开着「跟随最新版本」就立即生效；版本号变了，卡片上提示「重新读能力清单」。
  • 换密钥、停用：都由用户自己在卡片上操作。换新密钥要验证通过才会替换，同时提醒去 Nexus 停用旧的。
  • 系统功能：审批流用哪个 Agent 仍由运维配置，在调用测试里显示成「系统提供」。

6开发者的步骤怎么变

现在

10 步，其中 6 步要手动或半自动，3 步要碰到密钥

  1. 建 Agent（Operator）
  2. 平台内试用
  3. 建发布
  4. 签发调用密钥（网页）
  5. 把密钥交给运维
  6. 写进 secrets.env
  7. deploy.sh，服务重启
  8. 等刷新后被发现
  9. 手动读能力清单
  10. 改栈参数再部署，才能接入审批

B2：用户自己连接并启用

只剩签发、连接（一次）、启用三步要手动，都不用部署

  1. 建 Agent（Operator）
  2. 用 A2A 试用（try-agent）
  3. 建发布
  4. 签发调用密钥（网页）
  5. 连接 Nexus（只做一次）
  6. 在列表里启用
  7. 写文件
  8. 部署重启
  9. 立即可用，能力清单已读好
  10. 改了 Agent，刷新就是新版本

  3. 加载、测试、迭代

7以后：主入口是编码工具

Agent 的创建、更新和启用，以后主要在 Claude Code、Codex 或 Kiro CLI 里用自然语言完成，页面留给查看和兜底。所以这一期先把应用接口定成稳定的约定 agent-access-v1，页面、命令行和编码工具共用这一套。

你在编码工具里说Skill调用的接口
「在 Nexus 上建一个审批知识 Agent」nexus-ai-operator（已有）Nexus：建 Agent、写提示词、建发布
「给它签一把调用密钥」nexus-ai-operator要等 Nexus 支持方案 B；今天只能在网页上签
「在九安 PoC 里启用它」agent-access（新，Skills 设计）应用：POST /me/agents/:id/enable
「测一下」「改一下再测」两个 Skill 配合Nexus：改提示词；应用：重新启用、调用测试

这一期先提供命令行 skills/agent-access/scripts/agent_access.py，有 status、connect、enable、disable 四个子命令，密钥只经标准输入传入。编码工具现在就能直接调用它。以后会预留「应用个人令牌」（afp_），用来代替口令登录。

8我先替你定了的

不同意的话请指出来。

  1. 调用测试里同时列出「系统提供」的审批 Agent，所有人都能测试。
  2. 调用记录里，每个用户只看到自己的调用，以及审批流的调用。
  3. 启用时默认读一次能力清单，约 0.03 美元，可以取消勾选。
  4. 连接和启用都保存在实例的磁盘上，这一期不做备份；只有实例被替换才会丢。
  5. 断开 Nexus 连接时，不自动停用已经启用的 Agent。

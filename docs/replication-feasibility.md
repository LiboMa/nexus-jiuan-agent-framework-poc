# 深度调研：九安自助审核平台能否 1:1 复刻到 Nexus-AI

- 日期：2026-10-13
- 问题：把这个应用 **1:1 复刻**到 Nexus-AI 平台（https://d24xhqut5tas9k.cloudfront.net，v0.3.27 企业版）的可能性有多大？
- 方法：① 从代码里提取应用的完整功能清单（134 项，逐项带证据、权重、运行状态）；② 在 Nexus 仓库 `v0.3.27` tag 上逐项核对平台能力（应用中心、调度、数据连接器、凭据、VM、身份、审计、Bridge、MCP、OCR）；③ 用线上平台的实际配置做验证；④ 逐项对照打分。全程只读，没有运行应用代码。

## 1. 结论

| 复刻层级 | 定义 | 可能性 / 覆盖 |
|---|---|---|
| **L1 · 完全在 Nexus 上 1:1** | 不依赖 Nexus 以外的任何基础设施，行为与原版一致 | **≈ 0%**：7 项核心功能在 v0.3.27 上没有任何实现路径，另有 7 项核心存储功能没有承载位置 |
| **L2 · 在 Nexus 上高保真重建** | 允许自带数据库（RDS），业务逻辑改写成 Nexus 上的 Python 工具，界面改成 Nexus 应用页 | 56 项核心功能中：**57% 能保持原语义，30% 只能降级，13% 做不到**。不算 1:1；工作量按月计（粗估 3–6 人月） |
| **L3 · 混合（推荐）** | 平台按原样独立部署，Nexus 承担 AI 两项任务（及后续 AI 能力） | **100% 原有行为保留**；约 4.5–8 人日 |

**一句话：在 Nexus v0.3.27 上 1:1 复刻这个应用不可能；能 1:1 保留它的唯一方式是不搬它，让 Nexus 只接管 AI。**

## 2. 应用的真实画像（代码调研）

| 指标 | 数值 |
|---|---|
| 功能 | 134 项：98 项线上可达，2 项待接模型，13 项部分实现，6 项仅库代码，10 项仅命令行，2 项计划中，3 项不可达 |
| 核心功能（H） | 63 项 |
| HTTP 接口 | 56 个（34 个 GET、22 个写操作） |
| 数据库 | MySQL 8，56 张表、11 个迁移；AES-256-GCM 加密，数据密钥 32 字节 |
| 平台底座 | 16 张 Agent 卡（5 启用、6 暂停、3 手动、1 计划、1 冻结），只有 4 张有真实的执行适配器 |
| 界面 | 约 20 个视图（13 个哈希路由、9 个侧栏入口、单据详情窗约 11 个面板） |
| 代码 | `src/` 18,584 行（1.31 MB）；前端 JS 2,717 行（269 KB）；测试 26,369 行、1,173 个用例 |

**与设计方案不一致的地方（已抽查证实）**

1. **规则无法发布**：规则工作区的 `publish` 能力写死为 `false`（`src/analysis-rule-workspace.mjs:198`），规则通道实际运行时没有任何已发布规则。完整的生命周期（历史试跑、第二人确认、发布、回滚）只存在于库代码中，没有接口能调到。
2. **结论实际上不可能是「建议通过」**：列表和详情的基础预审调用时附件始终传空数组（`src/analysis-review-bridge.mjs:221`），「附件内容」永远是阻断缺口；AI 建议未完成也会计为一条风险（`src/analysis-verdict.mjs:291-297`）。
3. **跨单据扫描没有任何规则**，疑点台账没有接口和页面。
4. 没有运维 / 管理层角色；所有 `/platform/*` 只读接口对任何登录用户开放。

这意味着「1:1」要复刻的是一个**仍在开发中的产品**：目标本身还在移动（路线图有审批回写、按费用类型的审核 Agent 等）。

## 4. 逐类对照（56 项线上核心功能，按 L2 口径打分）

口径：允许自带 RDS；业务逻辑改写为 VM 内 Python 工具；调度用 Nexus 定时任务；界面为单个应用页；身份只用应用访问门。不含运维类 5 项（部署方式本就不同）和仅库代码的 2 项。

| 类别 | 核心项 | ✅ 原生 | 🟡 重建后语义一致 | 🟠 只能降级 | ❌ 做不到 |
|---|---|---|---|---|---|
| 身份与权限 | 7 | 0 | 0 | 2（共享口令代替会话；一主体一应用代替范围授权） | 5（钉钉登录、账号表、角色、管理员操作、双人确认） |
| 数据接入 | 10 | 0 | 7（汇联易客户端、规整入库、详情队列、明细整理、下载白名单、PDF 解析、锁与租约） | 3（增量同步、时间窗、按需取证都变成大模型触发） | 0 |
| 存储 | 7 | 0 | 7（全部依赖自带 RDS） | 0 | 0 |
| 审核逻辑 | 11 | 0 | 8（预审、规则卡、草稿、试跑、规则通道、两档结论、证据绑定、版本失效） | 2（每次读取计算 → 每次一轮 Agent；分层编辑权依赖身份） | 1（提案流转） |
| AI | 6 | 3（两项任务、模型接入） | 3（治理、脱敏、机械校验） | 0 | 0 |
| 界面 | 5 | 0 | 0 | 4（工作台、单据池、详情、规则库：每次查询 20 s 以上） | 1（登录） |
| 平台底座 | 10 | 1（暂停 / 恢复） | 3（调用中间件、单据进度、适配器） | 6（连接器登记、Agent 卡、运行器、调度器、改参留痕、审计追踪） | 0 |
| **合计** | **56** | **4（7%）** | **28（50%）** | **17（30%）** | **7（13%）** |

- **L1（不允许自带数据库）**：存储 7 项、依赖持久化的数据接入与审核逻辑约 15 项一起变成 ❌，可保持原语义的只剩 AI 等少数几项，覆盖 < 15%。
- **L2**：57% 原语义 + 30% 降级 + 13% 做不到。做不到的恰好是「合规」与「职责分离」，而这正是设计方案列出的四个目的中的第二个，对多主体财务平台来说不可放弃。

## 5. 线上平台的实际验证

| 项 | 线上取值 | 影响 |
|---|---|---|

## 6. 如果一定要「在 Nexus 上」：平台需要先补的能力

这些都是 Nexus 平台级的缺口；仓库里已有一份未实现的方案文档 `docs/_archive/app-center-l3-data-and-identity-plan-20260910.md`（「方案待评审，未实现」），覆盖了前两项：

1. **应用访客身份**：访客以平台账号（SSO）登录应用，页面拿到身份，会话按访客计量与授权。
2. **应用数据层**：应用自己的表 / 数据集，页面可直接读写，不经大模型。
3. **确定性步骤**：flow 里的 `tool` / `map` / `transform` 步骤（当前只是「预留」），以及不经大模型的工具调用。
4. **可靠的定时任务**：直接运行工具或脚本、重试与退避、任务超时、失败告警、卡住自愈、链式触发。
5. **行级数据范围**：权限能按资源属性（如公司）限定。
6. **运行时**：VM 提供 Node 24；OAuth2 客户端凭据自动换取与刷新令牌。
7. **网络**：Agent API 的超时、CloudFront 到源站的 HTTPS。

补齐这些之后，L2 才可能接近 1:1；以 v0.3.27 为基础，这是平台层面的大版本工作。

## 7. 建议

1. **按 L3 推进**：平台照原样部署，实现 `providers/ai-model.mjs` 调用 Nexus Agent（见 `assessment.md`）。这是唯一能保留 100% 原有行为、又让 AI 跑在 Nexus 上的做法。
2. **把 Nexus 的价值放在 AI 侧**：两项现有任务、Linux 下缺失的 OCR（视觉模型）、路线图里的「一句话写规则」与「按费用类型的审核 Agent」。
3. **如果客户的目标确实是「整个平台运行在 Nexus 上」**：先确认第 6 节的平台能力是否列入 Nexus 路线图；在那之前不建议启动迁移。

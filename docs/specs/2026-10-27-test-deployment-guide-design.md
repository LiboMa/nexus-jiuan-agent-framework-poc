# 测试部署指南：先在现有环境上跑通，再交给九安在他们的环境里部署（设计，2026-10-27）

状态：**已确认（2026-10-27）**：按此做；可以在 nxs-beine1013 上建演练用的 Agent 和发布、验完删掉；删掉线上提示词里那行杂项（写前给项目负责人看）。接在 v0.7.10（九安 v0.7.10 测试台、「Agent 接入」、制度知识库与库内语义检索）之后。

## 1. 要什么

一份 Claude Code / Codex / Kiro CLI 读得懂、照着就能执行的测试部署指南，覆盖整套交付：AWS 上的测试台（九安 v0.7.10 + 外壳）、知识库（PG + pgvector → Nexus 连接器）、Nexus 上的审核 Agent 与发布、九安前端的启用、端到端测试。

- 先在**现有环境**（我们的 AWS 账号、`nxs-beine1013`）上照指南跑一遍：各步应是「已是目标状态」，端到端测试通过。
- 之后**交给九安**，在他们自己的 AWS 账号和 Nexus 上照同一份指南从零部署、测试。

不做：生产部署、九安正式环境的接入（那是 `customer-rollout.md` 的事）；v0.5.3 PoC 的新功能（它仍随栈部署，因为 v0.7.10 的站点经它转发）。

## 2. 现状里挡路的东西（2026-10-27 摸底）

1. **环境值写死在代码里。** 栈的 VPC、子网、域名、托管区、证书、Nexus 地址只能改模板默认值；栈名 `andon-finance-poc` 写死在 6 个脚本里；`apply.py` 写死 Agent、发布编号、Nexus 地址和 operator 配置名；连接器编号写死在审核 Agent 提示词的第 4、7、9 条里。
2. **Nexus 一侧没有从零的自动化。** 没有脚本建 Agent、建 A2A 发布、给发布的动态配置绑连接器。调用密钥只能由发布者在 Nexus 网页上签发（接口回 403），这一步永远是人做。
3. **有几份文档还停在 v0.5.3。** 例如只列 v0.5.3 开发包（v0.7.10 也必须有）、`secrets.env` 样例缺 `JIUAN07_*` 两项、交接文档还写着「启用要填发布编号、名片要有契约两行」（补丁 0003 已去掉）。
4. 提示词里有一行网页上手工加的杂项（「请将：pgvector-andon (…) … 做为Agents as a Tool来调用」），带着测试台的私网 IP 和半截连接器编号。

## 3. 怎么做

### 3.1 一个环境一份配置文件

`poc/infra/env/<环境名>.env`（不进仓库；仓库里只有 `poc/infra/env/example.env`，逐项注释）。所有脚本用 `DEPLOY_ENV=poc/infra/env/<环境名>.env` 指定读哪份；不给就是现有环境（现在的模板默认值），所以现有用法不变。

内容：栈名、区域；VPC、子网、实例类型；两个站点的域名、回源域名、托管区、证书；Nexus 地址、operator 配置名；知识库放行网段；审核 Agent 名、发布编号（从零部署时由第 3.2 节的脚本建好后回填）。

改动：`deploy.sh` 把这些都作为栈参数传（现在只传 ImageId 和 KbAllowedCidr）；`destroy.sh`、`backup.sh`、`upgrade-instance.sh`、`bench-test.sh`、`run07.sh`、`kb.sh` 的栈名和区域从配置文件读；`apply.py` 的 Agent、发布、Nexus 地址、operator 配置名从配置文件读；端到端测试里写死的 `nxs-beine1013`、`us-east-1` 换成配置值。

### 3.2 Nexus 一侧：一个幂等的脚本

`audit-agent/setup.py`（和 `apply.py` 同一个目录、同一种写法：经 operator 调接口，写操作先 `--dry-run`）：

1. 按名字找审核 Agent，没有就建（克隆通用助手模板），写入提示词；
2. 按 Agent 找 A2A 发布，没有就建；写上描述；
3. 动态配置里绑上知识库的连接器（连接器由 `kb.sh connector` 建）；
4. 把 Agent 编号、发布编号打印出来，回填配置文件。

每一步先读现状，已是目标状态就跳过，所以在现有环境上跑应全是「=」。提示词里的连接器编号改成占位符 `${CONNECTOR_ID}`，下发时按配置替换；顺带删掉第 2 节第 4 条那行杂项。

调用密钥、九安「Agent 接入」页上的连接 Nexus、启用、设为审批 Agent：人做，指南里写清楚在哪个页面点什么、怎么核对。

### 3.3 指南本身

`docs/delivery/test-deployment.md`（交付文档，进交接仓库）：

- **开头一张表**：每一步谁做（编码工具 / 人）、要多久、会不会改动线上、怎么核对；
- **A 部分：在已有环境上部署、升级、核对**（我们现在这套）；
- **B 部分：在新环境从零部署**（九安）：准备配置文件 → 建栈 → 知识库 → Nexus 上的 Agent 与发布 → 签发调用密钥（人）→ 前端启用（人）→ 端到端测试；
- 每一步：要做什么、命令、期望的输出、出错看哪里；改动线上之前先 dry-run，把将要做的改动给人看，人同意再执行；
- 根目录加 `AGENTS.md`（Codex、Kiro CLI 读它）和 `CLAUDE.md`（Claude Code 读，引用 `AGENTS.md`）：硬规则（密钥、制度原文、先只读后改动、没确认不提交不推送）和指南入口。

同时把第 2 节第 3 条那些过时的说法改掉（固定规则：文档的每条流程说法都要和代码一致）。

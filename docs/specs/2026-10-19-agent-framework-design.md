# 设计：九安 Agent 接入框架

一页看全：[Agent 接入框架总览（HTML）](../delivery/agent-framework-overview.html)。细节在三份交付文档里，本文只写意图、取舍和边界：
- [Agent 接口：jiuan.agent/v1](../delivery/agent-interface.md)：信封、发现、调用、状态、错误码、限制、版本、怎么写新任务；
- [Agent 接入框架：架构、工作流与交付接口](../delivery/agent-framework.md)：架构、三类 Agent 怎么接、AI 步骤与审批流、七个交付接口、补丁分层、维护分工；
- [任务契约：单据初审 first_review@1](../delivery/first-review-contract.md)：第一个任务。

机器可读的契约：`audit-nexus/contract/`（`envelope/v1/`、`tasks/`、`workflows/`）。

## 1. 要解决什么

九安平台以后会接很多类型的 Agent：业务流程类（初审、分拣、按费用类型拆开的审核……）、财务类（费用分析、预算对比……）、知识库类（制度问答、推荐规则……）。我们要交付一套**框架**，包括补丁和接口描述文件，让九安的开发者（用编码工具）把这些 Agent 经 A2A 接进九安。第一个用上它的是审批流里的单据初审。

**第一标准是通用、解耦、以后好维护**，不是少写代码：九安的开发者用编码工具写，工作量不是问题。

## 2. 目标、非目标、反目标

**目标**
- 一套通用层（信封、发现、调用、状态、错误码、Agent 接入、路由、Agent 任务服务），所有 Agent 共用；
- 每类 Agent 一份任务契约；新增一类 Agent，只加任务契约和九安里这个任务的组装器与展示，**通用层不动**；
- 九安里只有一个文件知道 A2A；
- 第一个任务 `first_review@1` 跑通审批流：来单自动初审，失败自动重试一次，最后由人复核；客户发布的规则真正进入初审；
- 补丁按层交付，每层单独可打、自带测试；
- PoC 改成补丁的测试台，端到端测试即验收。

**非目标**
- 不碰汇联易：取单、同步是九安原有的事；
- 不给别的应用用：通用是指九安这一个平台上各种类型的 Agent；
- 本期只写 `first_review` 和 `describe` 两个任务的契约；财务类和知识库类的任务契约等真正接入时再写（框架已经为它们留好了调用方式、对象类型和长任务）；
- 不改九安原有的「AI 独立建议」和「草稿原件核验」；不回写汇联易；
- 本期不把「我的 Nexus」（每个账号连接与启用）并进九安。

**反目标**（技术上能跑通也算失败）
- 通用层里出现任何一个具体任务的字段；
- 每类 Agent 各写一套调用代码；
- Agent 需要懂九安的数据库、规则表结构或汇联易；
- 调用绕过九安的统一调用中间件（没有额度、日志、暂停开关）；
- Agent 做最终决定，或者直接改九安的数据；结果不经人复核就生效；
- 规则一发布就自动重跑、悄悄覆盖已有结论；
- 为 Agent 另配一套九安之外的密钥文件；
- 把 PoC 的锚点补丁、注入方式原样交给九安。

## 3. 约束

- **九安** v0.5.3 测试环境开发包：只读，不执行；裁剪过，补丁要在真实代码线上重新生成才能定稿。九安的原则：只读优先、不提交不退回；外部调用先登记成连接器；数据外发要过治理检查。
- **Nexus** v0.3.28：
  - A2A 只有文字输出，平台不检查格式，不推送；
  - 名片技能固定是一个 `ask`，只能改名称和描述；
  - 一次输入最多 10 万字；
  - 任务只留 24 小时，Nexus 重启就丢，重发不去重；
  - 每把调用密钥只对一个发布有效。

  详见接口文档第 8 节。
- **项目规则**：
  - 固定的四步使用逻辑：Operator 构建发布 → 应用经 A2A 发现 → vibe coding 做界面 → 测试上线；
  - 开发测试阶段不吊销、不轮换密钥；
  - 提交前要有端到端测试和项目负责人确认。

## 5. 我做的取舍（可以推翻）

1. **两层**：通用层（信封 `jiuan.agent/v1`）+ 任务层（`<任务>@<版本>`）；初审是第一个任务 `first_review@1`，输入输出的内容和上午定的一样。
2. **接入点**：九安的模型接入口 `providers/ai-model.mjs` 只加一个通用方法 `agentTask`，下面放我们维护的 A2A 适配层。调用记在哪张平台卡片上由 Agent 任务服务指定，暂停开关和调用日志按用法分开；额度现在整个连接器共用，按用法分要九安改中间件。
3. **发现**：名片描述里单独两行写「契约：jiuan.agent/v1」和「任务：名@版本」；内置任务 `describe` 可选，用来读更详细的能力清单。
4. **结果状态**：信封层只有「完成 / 拒绝」两种；拒绝表示这个请求不归这个 Agent 或它做不了，九安不重试、转人工。具体任务可以规定不用拒绝（初审就是）。
5. **三种调用方式**：一问一答、多轮对话（会话编号由九安保存）、长任务（到时限把 Nexus 的任务编号交回，稍后用 `tasks/get` 收结果）。
6. **AI 步骤**：九安里每次调用 Agent 都是一个 AI 步骤，状态、自动重试、作废、「依据已更新」对所有任务一样；任务在 `task.json` 里写清什么变了作废、什么变了只标记。
7. **任务清单 `task.json`**（有自己的 schema）：家族、调用方式、对象、公司还是租户级、谁能发起、结果怎么存、能不能分区、路由用哪些事实、能不能带文件、是不是长任务、检查、结果怎么推进流程、限制、数据类别、会不会改东西。九安的通用层只读这份清单，**不按家族写分支**；九安的数据治理按「数据类别」登记。
8. **租户级调用**：信封的 `context.scope` 可以是 `company`（一家公司）或 `tenant`（整个租户或集团层面，`companyId` 为空）。现在就定下来，免得以后为它出信封 v2。
9. **分区、路由事实、串联**：同一个对象可以拆成几份分别调用（分区编号由任务层给）；组装器交出路由事实，路由表只按这些名字比对；一个步骤的输出可以成为下一步的路由事实，串联由业务流程编排。
10. **三种调用方式**：契约里都定好。多轮对话和长任务随网关层做（第 7.2 节）：到时用测试专用的任务契约跑通；长任务由 Agent 任务服务自己定时收结果，重启时接着收，不依赖九安的调度。本期 MVP 只实现一问一答。
11. **补丁会改九安的几处平台代码**：`ai-model` 连接器在密钥来自启用记录时不再要求单独绑定；系统身份的受限授权；都标成安全相关，列进「要九安拍板的」。
12. **怎么测补丁**：补丁打在九安开发包的副本上，`source/` 下的原件永远不改。纯模块的测试在本机跑（和 PoC 现在的单元测试一样），要 MySQL 的测试在测试台上跑。
13. **检查代码跟着契约走**：每个任务的一致性检查写成不依赖任何东西的 JS，和契约一起交付；九安的适配层和 Agent 开发的自测用同一份。
14. **自动发起**（审批流）：九安平台流水线里加一站 `audit.first-review`，接在列表同步之后，找出当前版本还没有轮次的单据逐张发起。不接在明细整理之后：那一站只处理差旅报销单。
15. **原件**：预审前先用九安的读原件服务取原件文字；取不到也继续，要原件的规则判「缺材料」；原件后来取到了，标「原件已更新」，由人决定重跑。
16. **规则筛选**：公司、单据类型、生效期由九安代码（`resolvePublishedPolicies`）筛；规则和单据内容有没有关系、满不满足由 Agent 判断。字段核对类以引擎为准。
17. **规则发布与复核的角色**：规则发布沿用九安已有的「提交复核 → 独立复核 → 发布」；单据的人工复核由九安的 admin 或 analyst（能看这家公司）做。
18. **开关**：每个任务默认关闭，九安决定什么时候打开。
19. **时限**：初审一次调用 180 秒（九安允许的最大值），在测试台上用大单据实测；常常超时就在任务 v2 里把规则分几次发。
20. **一个发布一把密钥**：路由表只从「Agent 接入」里已启用、并声明了这个任务的发布中选；适配层按发布编号取密钥。
21. **存储**：AI 步骤的结果按任务 + 对象存；审批流状态每张单据一个键，不绑版本；都带版本号写；留痕最多 200 条；重启时中断的步骤标 `AGENT_STEP_INTERRUPTED`。
22. **现有知识 Agent**：它已经按任务组织，迁到信封上只改一版提示词；迁移期间，PoC 的调用测试面板同时认旧约定和信封。

## 7. 实施范围

### 7.1 本期：PoC / MVP

目标：在测试台上，用九安自己的运行时跑通「来单 → 预审 → AI 初审（经 A2A）→ 人工复核」，接口按 `jiuan.agent/v1` 和 `first_review@1`。

1. **契约**照现在的写法：信封 v1、`first_review@1`、`describe@1`。
2. **九安里只做初审跑通需要的部分**：
   - A2A 适配层，只做一问一答；
   - 模型接入口的 `agentTask`，以及连接器密钥的改动；
   - 「Agent 接入」（平台级启用）；
   - 简化的 Agent 任务服务：一问一答、按对象存结果、按单据类型路由、AI 步骤状态、自动重试一次；
   - 规则生效；
   - 初审组装器与审批流；
   - 流水线一站、系统身份；
   - 界面。
3. **Nexus 上的审核 Agent**：新提示词和发布。名片描述写契约和任务，固定版本。
4. **测试台**：现在这台实例原地升级到 t3.large，本机起 MySQL 8.0，跑九安的真实运行时（MySQL 存储、平台存储、调用中间件、流水线）。不接汇联易和钉钉，来单由测试写进九安的存储。现有的「我的 Nexus」「调用测试」继续可用。
5. **验收**：端到端测试通过、项目负责人确认后再提交；之后更新交付包、进度看板和文档。

### 7.2 以后：网关层

- 把通用层做成我们维护的独立网关模块，经插口用宿主的存储、身份、调用中间件、数据治理和留痕；
- 多轮对话、长任务、分区与串联、租户级调用、按用法分额度（契约里已经留好位置）；
- 财务类、知识库类任务；知识 Agent 迁到信封。

本期写的代码要给这些留出口子，但不提前实现。

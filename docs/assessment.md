# 实施难度评估：九安自助审核平台 → Nexus-AI

- 日期：2026-10-13
- 材料：`Andon-nexus-audit-platform/`（设计方案 docx + 测试环境开发包 v0.5.3 zip，原件未改动）
- 解压副本：`audit-nexus/source/审核平台-测试环境开发包-v0.5.3/`（文件名按 GBK 还原；只读分析，未运行任何代码）
- 目标平台：https://d24xhqut5tas9k.cloudfront.net（Nexus v0.3.27 企业版）

## 1. 结论

| 路线 | 难度 | 建议 |
|---|---|---|
| A. 整体迁入 Nexus（重写为 Nexus 应用 + Agent） | **很高** | 不建议 |
| B. 平台独立部署，Nexus 作为 AI 能力层（实现 `providers/ai-model.mjs` 调 Nexus Agent） | **中等偏低** | **推荐** |

这不是一个「Agent 应用」，而是一个**有状态的多用户财务预审平台**：AI 只是其中两个「参谋」任务，而且接口留空待接入方实现。
它的设计原则写明「编排由代码做，模型只在明确声明『调用模型』的步骤里出现（这是有意和让大模型自己决定下一步的通用 Agent 平台区分开）」。
所以最合适的做法是：平台照它自己的方式部署，Nexus 补上它缺的那一块——AI。

## 2. 应用概况

| 项 | 内容 |
|---|---|
| 定位 | 财务费用单据「预审 + 知识沉淀」：从汇联易只读同步报销单 / 对公付款单，规则通道做硬门禁，AI 通道补充风险分析，给出「建议通过 / 不建议通过」两档结论，每条结论可回溯到依据 |
| 技术栈 | Node.js 24（原生 ES 模块，无前端框架）+ MySQL 8；Docker Compose（app + mysql 两个容器，端口 4180）；Gitea Actions 部署 |
| 进程 | 单进程：HTTP 服务 + 内置调度器（每小时增量同步）+ Agent 运行器（流水线步骤） |
| 规模 | 产品代码约 **2.6 万行**（src 1.34 万、平台底座 4.8 千、前端 3.3 千、脚本 2.1 千）；测试约 **2.3 万行**（119 个文件） |
| 外部系统 | 汇联易测试租户（OAuth 只读）、钉钉（免登 + 工号绑定）、AI 模型（待接入） |
| 身份权限 | 钉钉工号 → 账号 → 可见公司范围；角色：审核员 / 规则负责人 / 发布复核人 / 运维 / 管理层；规则「一人写、另一人确认」 |
| 数据 | MySQL 加密存储（32 字节数据密钥）；结构迁移带结构核对；所有结论绑定单据 / 规则 / 附件 / 模型版本 |
| 附件 | PDF 文字：pypdf；**图片与扫描件 OCR 只支持 Windows（PowerShell 调 Windows OCR），Linux 容器里 `AI_DOCUMENT_OCR=off`** |
| AI 任务 | `advisory`（独立审批建议）与 `reviewDraftEvidence`（规则草稿原件核验）；输出 JSON Schema、机械校验函数、错误码都已定义；中间件策略：超时 120 s（可调 1–180 s）、不重试、并发 2、**每日 150 次** |
| 包内缺失 | 正式环境、SAP、AI 实现、全部凭据与数据（需客户另行提供汇联易测试租户 OAuth 与钉钉应用凭据） |

## 3. 路线 A 为什么难：与 Nexus 应用模型的冲突

| 平台需要 | Nexus v0.3.27 能提供 | 冲突 |
|---|---|---|
| 多页工作台：单据池、列表筛选、下钻、规则库编辑、运维页 | 单文件页面（≤ 2 MB），沙箱 iframe，禁止 `fetch`，**每个动作都是一次 Agent 调用** | 列表查询走 Agent，每次 20 s 以上且耗模型额度；也违背平台「编排由代码做」的原则 |
| MySQL 事务存储、加密、迁移、版本绑定 | 数据连接器（供 Agent 读取外部数据），不托管应用数据库 | 没有应用自己的存储层 |
| 钉钉工号登录、按公司范围授权、规则双人确认 | 应用访问控制只有「无验证 / 访问验证」级别 | 做不到按用户的数据范围 |
| 每小时增量同步、附件下载 / 解析队列、跨单据扫描 | 定时任务 = 定时让 Agent 跑一轮 | 数据管道不适合交给大模型编排 |
| 2.6 万行业务代码 | — | 重写成本以月计，且要重新验证全部口径 |

另外，nexus-transform 也不适用：它转换的是 LangChain / AutoGen 等 Agent 框架代码，而这里的「Agent」是代码编排的流水线步骤，不是大模型 Agent。

## 4. 路线 B（推荐）：独立部署 + Nexus AI 层

```
审核平台（Docker Compose：Node 24 + MySQL 8）
  └─ providers/ai-model.mjs  ──POST /api/v2/app-api/{app_id}/{idx}/invoke（X-API-Key）──▶ Nexus 应用
        ▲ 返回 {text, data}                                                              ├─ Agent 0：审批建议（ADVISORY_TASK + ADVISORY_SCHEMA）
        └─ parseAdvisoryResult / validateDraftEvidenceResult（平台自带机械校验）           └─ Agent 1：草稿核验（DRAFT_EVIDENCE_TASK + 其 schema）
```

**为什么契合**

1. 接入点已经设计好：只需实现 `createModelClient`，返回 `{model, dataPolicy, advisory, reviewDraftEvidence}`；调用方、中间件（超时 / 限流 / 额度 / 日志）、页面文案都不用改。
2. 提示词与输出 schema 直接取自 `ai-model.mjs` 里的 `ADVISORY_TASK` / `ADVISORY_SCHEMA` / `DRAFT_EVIDENCE_TASK`，放进 Nexus Agent 的系统提示词与 `output_schema`；Nexus 负责模型（Bedrock Claude）、提示词版本、调用记录与用量统计。
3. Nexus 的应用 Agent API 是请求-响应式，返回 `{text, data}`，套用 Agent 的输出 schema，带所有者预算与应用配额闸门；实测单次 Agent 调用约 20 s，低于平台 120 s 超时。
4. 平台自己的机械校验（结构、枚举、长度、引用逐字匹配）仍然生效，模型输出不合格不会形成结论。

**工作项与估算**（粗估，前提：客户提供凭据、测试租户可用）

| # | 工作 | 估算 |
|---|---|---|
| 1 | 部署测试环境：Docker Compose、MySQL、配置文件（`deploy.sh config-json` 可生成样式）、数据密钥、汇联易 OAuth 与钉钉凭据、钉钉可访问的 HTTPS 域名 | 1–2 天 |
| 2 | Nexus 侧：两个 Agent（提示词 + 输出 schema）、绑定到一个应用并发布（设为长期有效）、生成 Agent API Key | 0.5–1 天 |
| 3 | 实现 `providers/ai-model.mjs`（约 100–200 行）：请求组装、错误码映射（429 → `AI_RATE_LIMIT`，超时 → `AI_UNAVAILABLE` 等）、usage 透传；单元测试 + 用平台自带校验函数做契约测试 | 1–2 天 |
| 4 | 联调与评测：测试租户真实单据上看结构化输出通过率、引用逐字匹配率、时延、单次成本 | 2–3 天 |
| | **合计** | **约 4.5–8 人日（1–1.5 周）** |

**可选增强（Nexus 能额外补上的）**

| 增强 | 价值 | 估算 |
|---|---|---|
| 图片 / 扫描件识别：新增 OCR provider，用 Claude 视觉能力替代 Windows OCR | Linux 部署下目前识别不了扫描件，这是证据链上的实际缺口 | 2–4 天（另需数据出境评估） |
| 路线图「一句话让 AI 写规则」：Agent 只接收一句话 + 字段名称表，输出规则卡 | 方案 8.4 的主路径，天然适合做成 Nexus Agent | 2–3 天 |
| 路线图「按费用类型的审核 Agent」 | 每个末级费用类型一个 Agent，Nexus 管理提示词版本 | 按类型逐个推进 |

## 5. 前置条件与风险

| # | 事项 | 影响 | 处理 |
|---|---|---|---|
| 1 | 汇联易测试租户 OAuth 凭据、钉钉应用凭据不在包内 | **最大阻塞**：没有就无法部署出可用环境 | 向客户申请，或用我方自己的测试租户与钉钉应用 |
| 2 | 数据出境：单据字段与脱敏附件文字会进入 Nexus 会话记录（默认不自动清理）并发往 Bedrock | 方案 7.4 明确要求接手方评估 | 与客户确认模型所在区域与数据条款；配置 Nexus 会话清理 |
| 3 | Nexus 平台自身的安全与稳定：admin 默认口令且登录页显示、SSH 全网开放、刚发生节点失控事故 | 作为生产依赖前必须加固 | 见 `incidents/` 与迁移报告的风险清单 |
| 4 | Agent API 要求应用处于发布状态，发布有到期时间（本平台默认 30 天） | 到期后 AI 静默失效 | 发布时设为长期有效，或纳入运维巡检 |
| 5 | 每次调用新建会话、启动 VM：时延约 20 s 以上；预算 / 配额闸门可能返回 429 | 「单据到达即自动初审」时的吞吐 | 当前每日上限 150 次、并发 2，够用；429 映射为可重试错误 |
| 6 | 模型能否稳定按 schema 输出、逐字引用附件原文 | 不合格就不形成结论 | 列入第 4 项评测，必要时调整提示词或切片 |
| 7 | 计费归属：Agent API 的用量记在应用所有者名下 | 成本核算 | 用独立账号作应用所有者 |
